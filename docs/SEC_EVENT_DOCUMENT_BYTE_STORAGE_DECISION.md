# SEC event-document byte storage decision

Decision contract: `sec-event-document-byte-storage-decision/v1`

Reviewed and official-source control date: 2026-10-02
Status: technical candidate selected; production remains `BLOCKED_BACKEND_UNAPPROVED`.

This is a design decision only. It creates no storage adapter, SQL, migration, repository, live acquisition, or persisted bytes. A technical selection does not approve live acquisition, raw-byte storage, normalized storage, authority persistence, retention, redistribution, or commercial use. Each remains `NOT_APPROVED` pending its own source, legal, usage, security, backup, and operations review.

## Decision

Choose **A: PostgreSQL `bytea` content blobs plus separate immutable SEC artifact/package authorities in one PostgreSQL transaction** for the first production-capable architecture. If PostgreSQL is hosted by Supabase, the same database transaction can include these application tables; Supabase Storage buckets are not used for authoritative bytes in v1. This provides one database commit/rollback and backup/restore scope for the app's rows. It does not establish a provider durability SLA, RPO/RTO, or that Supabase Storage object bytes are in database backups. It is a candidate architecture, not permission to deploy it.

Technical, operational, and approval judgments are separate: A is technically and operationally suitable within the limits below; no candidate has production approval. The source-provenance decision remains the authority for SEC identity boundaries; this contract specifies the byte backend only.

## Versioned byte identity

The strict `sec-event-document-byte-storage-decision/v1` binds the byte contract version, backend kind, SHA-256-derived blob ID, lowercase SHA-256 over the exact HTTP entity-body octets, byte length, validated content type, content-encoding policy, provider and immutable source-profile identity/fingerprint, filing-package ID, canonical document locator, and document role. The digest input is the entity body after HTTP transfer framing has been removed by the HTTP client but before charset decoding, text extraction, newline conversion, Unicode normalization, or parsing. Request `Accept-Encoding: identity`; reject an unexpected `Content-Encoding`. No decoded/extracted string is an acceptable substitute.

`blobId = "sha256:" + lowercaseHex(SHA256(entityBodyOctets)) + ":" + decimalByteLength`. The blob table's logical key is `(sha256, byte_length)` and also has a unique digest-only guard: a repeated digest with an inconsistent length is rejected. On a key conflict, reread bytes and compare them exactly; a same-digest/same-length but different byte sequence is treated as a SHA-256 collision and fails closed. The hash and length are calculated from bytes, then compared with any declared index/manifest metadata. `storedAt`, receipt, readback time and verification event are receipt/audit metadata and do not enter document-artifact identity.

Blob identity is intentionally narrower than document identity. One immutable content blob can be referenced by distinct document artifacts when identical bytes appear at different SEC locators or roles. A document artifact binds source profile and fingerprint, filing identity, canonical locator, role, media type, byte length, byte/canonicalization contract version and blob digest. Package membership is a separate ordered relation and does not rewrite either identity. Receipts/availability and sealed event-source lineage/members are separate append-only authorities; event authority remains a later, blocked boundary.

Canonical locators are SEC archive-relative paths only, with canonical separators and no scheme, authority, query, fragment, dot segment, percent-decoded traversal or alternate spelling. Media type is descriptive metadata, not proof: validate permitted type against magic/grammar appropriate to the declared document kind without transforming the bytes used for the digest.

## Limits and transaction shape

| Bound | v1 limit | Basis |
|---|---:|---|
| One document | 8 MiB (8,388,608 octets) | Local safety/transaction and memory cap, not PostgreSQL's documented field maximum. Leaves room for filing exhibits while bounding whole-value hashing/reread. |
| One filing package | 64 MiB (67,108,864 octets) aggregate | Local safety cap; bounds one transaction, WAL burst and backup growth. |
| Documents per package | 32 | Local cap sized for index, primary filing and a bounded exhibit set; reject larger packages rather than silently truncate. |
| Receive / digest | Bounded streaming into a capped transaction-owned buffer; reject as soon as a limit is exceeded. | v1 does not use chunk tables or PostgreSQL Large Objects. |
| Acquisition timeout | 15 seconds per document | Local request budget; incomplete streams are rejected and never persisted. |
| Readback | In-transaction bytea reread; compare length and recompute full SHA-256 before commit. | No partial/range result may establish full-object authority. |
| Memory | At most one package worker and one document database query active per worker; cap one retained `Buffer` per acquired document. Budget 96 MiB per active package worker: 64 MiB package buffers + up to 8 MiB driver parameter copy + one 8 MiB returned bytea row + 16 MiB headroom. | Conservative local process budget; validate the actual driver's copies before implementation. |

PostgreSQL documents binary `bytea` as raw octets, TOAST compression/out-of-line storage as transparent to SQL users, and a 1 GB field limit. A `SELECT` returns the logical `bytea` value; TOAST's physical compression/chunk representation does not change that logical byte sequence. The design claims logical entity-body byte identity, never physical page/media identity. The 1 GB value is a platform limit, not a safe application limit. TOAST does not remove WAL, table/TOAST bloat, backup, whole-value memory or restore costs. A v1 query never selects bytea in list views; only bounded server-only reads load it. Avoid UPDATE churn; immutable inserts reduce, but do not eliminate, MVCC/WAL and vacuum costs. Migration cost is schema-light but backup and restore costs scale with accumulated bytes. Do not use the separate Large Object facility: it has a distinct transaction-scoped stream/lifecycle model with no benefit inside this bound.

The package is acquired sequentially before opening the database transaction: each raw response is counted and incrementally hashed in 64 KiB chunks, retained as one bounded `Buffer`, and rejected immediately if document, total package bytes or member-count limits are exceeded. Use checked integer addition over observed byte lengths. Do not decode, base64/hex expand, `Buffer.concat` duplicates, or keep another decoded representation. During the transaction, issue one blob insert/readback at a time; never fetch all package bytea values as a 64 MiB aggregate. The chosen Node PostgreSQL driver's parameter/result buffering is not claimed to stream; driver memory behavior must be measured against the 96 MiB worker budget before implementation. If it cannot meet the budget, reduce limits or select/document a streaming API in a later review. Transaction timeout/cancellation rolls back all package rows.

## Write/readback protocol

Minimal states: `RECEIVED -> BYTES_VERIFIED -> AUTHORITY_COMMITTED`, with terminal `REJECTED`. A failed commit leaves no durable intermediate state. On connection loss with unknown commit outcome, retry performs an authoritative lookup and verifies the complete row; it never assumes failure or success.

1. Receive exact entity-body octets after HTTP transfer framing. Send `Accept-Encoding: identity`, disable transparent decompression, and reject any unexpected `Content-Encoding`. Incrementally hash/count raw chunks before charset decoding, HTML parsing, newline/Unicode normalization or extraction; do no such conversion for persistence. The application computes this first SHA-256.
2. Enforce actual per-document length, running package sum and member count while streaming. Reject/cancel at 8 MiB, 64 MiB, 32 members or 15 seconds. Compute blob key from lowercase digest plus decimal byte length. No base64/hex body expansion.
3. In one PostgreSQL transaction insert-or-read the content blob, reread one logical bytea, recompute SHA-256 in the application, compare exact length and bytes, then release the result buffer. No `pgcrypto` extension or database-side hash is assumed.
4. Insert the distinct artifact authority, filing-package authority and ordered package members. Acquisition receipts/availability and event lineage/members are separate approval boundaries and are not written by this v1 byte/package transaction. Reread the complete byte/package authority graph and each referenced blob one at a time. Commit only after all hashes, lengths, scopes and member sets verify. Any error, timeout, cancellation or integrity mismatch rolls back all package writes.
5. Later authoritative reads resolve an artifact authority to its content blob, retrieve one logical bytea, and repeat application-side digest/length verification before returning bytes. Missing row, null/short bytes, mismatch or database error is fail-closed; record a separate sanitized integrity incident without changing old authority.

Atomicity for this slice's eventual byte/package UoW covers new blob, artifact, package and member rows in one PostgreSQL transaction. Later separately approved receipt or lineage work must define its own transaction boundary. This does not include SEC's server or external approvals. Crash before commit rolls back every new row. A committed-but-later-missing/mismatched row is a database integrity/restore incident, not an orphan to rewrite silently. Restore a verified consistent backup or append a reviewed correction.

Use `READ COMMITTED` and exact unique constraints as concurrency arbitration; `SERIALIZABLE` is not required for immutable insert/read operations. Insert-if-absent may use `ON CONFLICT DO NOTHING` only on the exact immutable key, followed by a separate authoritative `SELECT`; `DO UPDATE`/upsert is forbidden. Sort content/artifact/package keys and acquire them deterministically. Concurrent identical writers converge only after reread verifies the already committed row. Conflicting bytes/material reject. Serialization/deadlock/timeout/uncertain commit is surfaced sanitized; the UoW has no hidden retry. A caller retry performs authoritative lookup and complete verification. No cross-service orphan can exist; unreferenced provisional blob rows are never promoted outside a complete verified transaction.

## Security, backup, retention, cost

All access goes through a server-only adapter and a dedicated command path. Resolve the direct PostgreSQL credential only at the final server boundary. Supabase service-role/storage keys are unnecessary for this UoW and must not be introduced. Never return raw database errors, secrets, credentials, entity bodies or secret-bearing paths in logs/results. Deny by default; no browser DB/storage credentials or client insert/update/delete. For every exposed `public` authority table, enable RLS with no policies and revoke table/function privileges from `PUBLIC`, `anon` and `authenticated`. Enforce immutable `UPDATE`/`DELETE` rejection triggers. Any narrowly scoped database function is `SECURITY INVOKER`, has a fixed `search_path`, and has `EXECUTE` revoked from `PUBLIC`, `anon` and `authenticated`; no `SECURITY DEFINER`, generic write API, public view, or byte-download path is allowed.

PostgreSQL database backup/PITR includes database table values such as bytea when those database backup methods cover the database; validate hashes after restore. This is not a durability SLA or RPO/RTO promise. Supabase explicitly distinguishes Storage object bytes from Postgres `storage` metadata: its database backups include the metadata but do **not** include Storage API object bytes. Do not describe database backup of `storage.objects` metadata as backup of actual object payloads. Supabase Storage object GB-hour/egress pricing is a separate billing dimension; no provider quote or cost approval is implied. Local logical backup/restore must include bytea and validate fingerprints. Local tests can use pure octet fixtures and the project's PostgreSQL test boundary; no CLI, Docker or backend was used in this slice.

Supabase documents compatibility with selected S3 APIs, including ranged `GetObject` and conditional `GetObject`/`HeadObject`; this is protocol/API compatibility, not a general guarantee of all S3 semantics. A partial range cannot verify full-object identity. Its compatibility matrix explicitly lists S3 Versioning as unsupported and marks the listed S3 Object Lock operations as unsupported; this describes the published compatibility surface, not a claim about every possible platform feature. The S3 docs do not document ETag as SHA-256. The Storage lifecycle API documents current-object expiration as rejected and only noncurrent-version expiration; because S3 versioning is unsupported, it does not provide the needed current immutable-object retention policy. Storage API deletion is documented as permanent. None establishes provider durability or write-once retention for option B.

Normal `UPDATE`/`DELETE` is prohibited. Corrections append new authority and explicit supersession; old evidence is not overwritten. But perpetual immutable retention can conflict with legal deletion: retention and deletion are both `NOT_APPROVED`, and this decision does not resolve the conflict. No automatic expiry or legal deletion is implemented. Any future deletion requires a separate authorized administrator workflow and an approved policy naming the authorizer, evidence, scope, audit record and hold check. The policy must decide tombstone versus physical deletion and describe impacts on shared blobs, document manifests, package membership, receipt/availability, lineages and previous claims. A tombstone does not erase bytes. Physical erasure cannot be claimed until references and database backups/WAL/PITR restore copies expire or are separately purged, with a documented completion window. Those deletion mechanics and effective erasure time remain BLOCKED; no actor is presently authorized. SEC usage terms, raw-byte storage, retention, redistribution, commercial use and legal basis remain separate blockers.
