# Dashboard setup for a standing PAPER_ONLY policy

The dashboard can create a dedicated PAPER/NOK account from its empty state, then create a versioned `standing-paper-policy/v1` policy for that account. Account creation derives the owner from the authenticated server session; the request body accepts no owner, mode, currency, deposit, or ledger fields. A transaction-scoped advisory lock keyed by owner serializes duplicate requests across processes. A repeat finds and returns the same eligible empty PAPER/NOK account. The database creates its two empty ledger-account taxonomy rows through the existing account trigger, but account creation writes no ledger transaction, ledger entry, deposit, policy, or worker state. There is no schema change.

The policy command checks ownership, active status, PAPER mode, NOK currency, ledger emptiness, and absence of another policy while holding the account row lock. Concurrent attempts for the same account cannot create duplicate policy drafts. No virtual contribution, order, or fill is created.

Creation stores a `DRAFT` policy and one `INITIALIZE` transition in a transaction. The repository locks the account row, then checks ownership, status, mode, currency, ledger emptiness, and existing policy before inserting either row. Concurrent requests for the same account serialize on that account lock; only the first can create a draft. No virtual contribution, order, fill, or worker is started.

The owner chooses one or more supported fixture instruments, capital budget, maximum order, maximum position, total gross exposure, maximum contribution-adjusted loss, and maximum price age. Limits use NOK minor units internally and decimal NOK strings at the API boundary. The capital budget is bounded to 100–1,000,000 NOK. Order and position limits must be positive; the loss limit can be zero. The ordering is `max order ≤ max position ≤ max gross exposure ≤ capital budget`, and the loss limit cannot exceed the capital budget. Price age is one of 15 minutes, 1 hour, 24 hours, or 7 days. Server-side validation is authoritative.

First activation is separate from creation. The DRAFT card shows the policy identity, version, allowed instruments, and every selected boundary. The owner must check an explicit confirmation box. The request sends the expected `DRAFT` status and a SHA-256 confirmation hash over the exact policy identity/version/account/mode/status, instrument list, and risk/freshness boundaries. Within one transaction the repository locks policy then account (matching worker and transition lock order), rechecks account ownership and runnable `ACTIVE/PAPER/NOK` state, checks the expected status and hash, and writes the policy status plus append-only transition history. A changed policy or stale/double-click request cannot activate unseen terms. Activation does not start a worker.

Policy status is independent of worker status. Dashboard values are stored PAPER data. Any later worker input prices are synthetic fixture values and fills are simulated under the repository's documented simulation assumptions; neither is an exchange execution or evidence of live market performance. This feature adds no broker, provider, or live-trading path and makes no hosted database changes.
