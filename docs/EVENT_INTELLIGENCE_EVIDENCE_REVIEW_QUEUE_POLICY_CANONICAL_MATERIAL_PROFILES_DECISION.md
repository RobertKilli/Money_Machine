## Recommended material and identity profile

Each family needs a closed schema with explicit family, material-profile version, canonicalization-profile version and policy/algorithm semantic-contract version. Proposed canonicalization is compact UTF-8 JSON: object keys recursively sorted by UTF-16 code units; arrays preserve order where order affects meaning; each set field is tagged as `SET` by its closed schema/profile, deterministically sorted by the same comparator, and rejects duplicates. The profile determines whether each field is a set or ordered array. Strings are Unicode scalar sequences: quote and reverse-solidus are escaped; U+0000 through U+001F use JSON short escapes for backspace, tab, line feed, form feed and carriage return, and a lowercase `u` escape with two leading zero digits for the remaining controls; slash and other scalars are emitted unescaped as UTF-8. Reject lone surrogates. Numbers are safe integers only, emitted as minimal base-10 digits with no plus sign, leading zeroes or exponent notation; reject negative zero, fractions and non-finite/unsafe numbers. There is no trimming, case folding or Unicode normalization. Reject getters/accessors, custom prototypes, symbols, sparse arrays, cycles and unsupported values. Unknown fields and versions fail closed. The future profile must specify bounded strings, depth, nodes, collection lengths and byte budgets and reject atomically rather than truncate.

Recommended exact content-identity preimage:

```text
ASCII("event-intelligence-policy-content-identity/v1") || 0x00
|| UTF8(familyTag) || 0x00
|| UTF8(materialProfileVersion) || 0x00
|| UTF8(canonicalizationProfile) || 0x00
|| canonicalMaterialBytes
```

The first line means the ASCII bytes of the literal domain text followed by exactly one NUL byte; quotation marks in the code notation are explanatory and are not hashed. Every displayed `0x00` is exactly one separator byte. `familyTag` is exactly one of `ISSUER_LISTING_POLICY`, `SOURCE_PORTFOLIO_POLICY`, `ROUTING_POLICY` or `QUEUE_CONTRACT`; `materialProfileVersion` is exactly the corresponding profile identifier in the matrix; `canonicalizationProfile` is exactly `event-intelligence-policy-canonical-json/v1`. These identifiers are ASCII, at most 128 bytes each and cannot contain NUL, so field boundaries are unambiguous. Each closed family material schema also includes its policy-contract and algorithm-semantic version as ordinary canonical JSON fields within `canonicalMaterialBytes`; those versions are never inferred from the outer tags. `canonicalMaterialBytes` are the complete compact canonical JSON bytes with no final separator, BOM, whitespace or newline. The digest is lowercase hexadecimal SHA-256 of that complete preimage. The domain, family, material profile and canonicalization profile are bound outside the material bytes; no digest is included in its own preimage. Any future byte limit must state separately whether it bounds canonical material bytes or the whole preimage including domain separators. The profile identifier is proposed design, not an implemented hash format.

Content identity addresses exact material under a named profile. Semantic identity additionally depends on a reviewed policy/algorithm contract and conformance behavior: a parameter table digest does not identify all executable code semantics. Do not substitute function-source, build-output or Git-SHA hashing. If behavior cannot be semantically closed, that family remains blocked. Transitive references must be typed family/profile/content-identity edges with finite acyclic closure, explicit resolution, and rejection of missing/ambiguous targets; no implicit defaults or self-reference.

## Separate identity and authority layers

1. **Reference syntax:** current scope v1 accepts identifiers, versions and digest-shaped strings.
2. **Policy content identity:** a future profile recomputes a digest from validated canonical material and compares it with an independently trusted expectation. No such verifier or expectation source exists here.
3. **Policy semantics:** a reviewed, versioned contract and conformance evidence define behavior, including code-level rules.
4. **Application:** the module applying validated policies must produce local evidence during one concrete composition, bound to exact inputs, selected semantic versions, cutoff and result. A matching declaration supplied later is not evidence of application.
5. **Approval/authority:** registry membership, approval, access authorization, rights, producer authority and domain authority are separate gates.

The existing application contract remains `VALID_SYNTAX_ONLY_NON_AUTHORITATIVE` and `MISSING_RUNTIME_RESULT_BINDING`. Two caller declarations that agree do not prove that either is authentic or was applied. A repeated digest/reference does not prove application, approval, access or producer readiness. Scope identity remains unchanged and excludes cutoff, snapshot/manifest digests, artifact IDs, receipt time and UI filters. Priority-bearing policy arrays are ordered and must not be treated as membership sets.

## Blocked production state

The companion closed decision parser only compares supplied material to the fixed decision and returns a syntax/decision status. It does not verify policy content or prerequisite completion. Its defensive traversal limits are depth 12, 10,000 visited values, 4,096 UTF-16 units per string, 64 own properties per object, and 128 entries per array; the fixed v1 decision is within these bounds. The parser returns the fixed frozen decision, not caller-owned data. Production config has no selected verifier strategy or resolver; active profile, policy and producer registries are empty; content verification, application evidence, producer, persistence, storage read and current selection are `BLOCKED`; approval, rights, retention, deletion and access authorization are `NOT_APPROVED`; authority upgrade is `UNSUPPORTED`; signal and trading are `BLOCKED`. No loader or runtime imports this decision module.

## Compatibility and next prerequisite

Do not alter scope v1 canonical profile, domain prefix, golden identity or the 18,264-byte scope-material limit. Introducing family/profile-tagged content identities changes the meaning/shape of references and needs a separately reviewed scope-material v2. Snapshot, manifest and binding wire contracts remain unchanged. This slice adds no resolver, content verifier, runtime application, registry or producer.

Recommended next bounded prerequisite: decide and specify canonical semantic-material projections for the already tracked source-portfolio and queue rule tables, including explicit algorithm-contract versions and conformance cases. These have concrete rule data to anchor. Keep issuer/listing and independent routing material blocked until their missing contracts are defined; do not proceed to a resolver until each profile has closed semantics and approved expectation/registry requirements.
