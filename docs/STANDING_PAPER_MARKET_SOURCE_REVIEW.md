## Scope and recommendation

The [offline standing PAPER price contract](STANDING_PAPER_POLICY.md#external-paper-price-contract-offline) requires an exact external instrument/source binding, `LAST_TRADE`, `BID` or `ASK`, a price-observation time, an evidenced availability time and receiving-side retrieval time. Quote currency must equal the PAPER account currency; this path does not convert currency. Fixture instruments are excluded. `AVAILABLE` in that contract is a receipt-validation result, not source permission.

**Recommended first technical candidate (conditional, not approved): Kraken Spot REST `Post-Trade Data` (`GET /0/public/PostTrade`), `LAST_TRADE`, one explicitly mapped pair such as `ETH/USD`.** Its documented response carries a trade identifier, decimal price, pair/base/quote, execution venue, engine-match `trade_ts`, and market-data publication `publication_ts`. That is a closer fit to the contract's timestamp and traceability requirements than Kraken's Ticker snapshot. Two material endpoint semantics remain unresolved: how to guarantee that the selected record is the latest eligible trade, and how source timestamp precision maps safely to the millisecond contract (below). Before any external ingestion or use, confirm exact pair/venue mapping, qualify those semantics, confirm that `publication_ts` qualifies as `availableAt`, and obtain written permission for this project's automated PAPER processing and intended storage/display if required. Public unauthenticated access is not permission. Until those gates are recorded, external source status remains **BLOCKED / NOT APPROVED**.

The candidate product returns a USD quote in the example pair. The first USD product would therefore require a separate PAPER account denominated in USD. Do not map its price to a NOK account or infer an FX rate. If a NOK-denominated first account is required, choose and separately qualify an exact NOK-quoted instrument instead.

## Transport plan for the conditional Kraken candidate

This is a proposal for a later, separately approved adapter; it performs no network action by itself.

1. **Request scope:** fixed HTTPS origin `api.kraken.com`, fixed path `/0/public/PostTrade`, exactly one pre-registered pair per request, `symbol=ETH/USD`, and no caller-supplied host/path/query. The official docs define `count` as a maximum number returned (up to 1,000), not as “return the newest N”; do not use `count=1` as proof of latest-trade selection. Before an adapter may emit `LAST_TRADE`, obtain official semantics for a latest-trade request or use an explicitly qualified streaming/current-trade mechanism; otherwise leave latest selection blocked. No pagination or historical backfill in the first slice. One source request per instrument per worker round; a local process cap of one request per second and one in-flight request globally. Do not retry, fail over, or call fixtures after an error.
2. **Network bounds:** enforce TLS certificate verification, fixed host/path allowlist, connection and total deadlines (proposed 2s connect / 5s total), bounded response body (proposed 64 KiB), JSON content-type, and strict schema. These are proposed client limits, not Kraken guarantees. Do not log credentials or raw provider payloads.
3. **Timestamp resolution and validation:** Kraken describes `trade_ts` as microsecond precision, while its ISO 8601 examples carry nine fractional digits; the current PAPER contract accepts canonical UTC timestamps with exactly three fractional digits (milliseconds). Preserve the provider's original timestamp strings byte-for-byte in source evidence. For contract comparison, propose a lossless parser into integer nanoseconds (or finer exact decimal fraction), then normalize without rounding-to-nearest: floor `observedAt` to the prior millisecond so the trade is never represented as newer than it was; ceil `availableAt` from `publication_ts` to the next millisecond so eligibility is never moved earlier than publication; and represent receiver-side `retrievedAt` as a conservative millisecond upper bound (ceil a high-resolution wall-clock receipt time, or add one millisecond to a millisecond-only capture). Reject if normalized ordering fails or if conservative retrieval moves beyond the decision cutoff. Never truncate `availableAt` downward or round any source timestamp to nearest. Require exact pair/base/quote, qualified venue, nonempty `trade_id`, positive decimal `price` parsed exactly, and `observedAt <= availableAt <= retrievedAt <= decision cutoff`. Reject malformed/missing values, unexpected currency/venue, future values, and age over policy. A 200 response with no usable trade is missing data and blocks.
4. **Evidence:** persist an immutable normalized receipt bound to provider/product/version, mapped external instrument ID, venue/pair, `LAST_TRADE`, original decimal price, normalized integer price, trade ID, `trade_ts`, `publication_ts` as availability (only after qualification), receiver `retrievedAt`, request fingerprint without secrets, response/payload fingerprint, and decision price fingerprint. Retain only fields needed for audit under an explicitly approved retention policy; permission for raw response retention is unresolved.
5. **Failure behavior:** timeout, TLS/DNS/connectivity failure, 429/rate-limit response, provider error, missing/invalid values, stale/future timestamps, or permission/readiness failure returns blocked/unavailable with no price. No stale cache, alternate provider, synthetic fixture, FX conversion, or simulated fill may mask a source failure.
6. **Rate ceiling:** although Kraken documents the public-data safe guidance of no more than one REST call per second, the product-level cap proposed here is much lower: at most one single-pair request per policy/instrument per worker round, and never exceed one request/second per source IP. Honor 429 and stop the round; no automatic retry.

## Required evidence before source approval

- Written response from Kraken covering this project's automated PAPER use, algorithm testing/validation, service audience, storage/retention, display and any derived output; identify any applicable fee or subscription and geographic restrictions.
- Official static evidence for the exact active pair, base/quote, canonical venue MIC and whether `ETH/USD` maps unambiguously to the selected product. No ticker-only identity mapping.
- Documented confirmation that `publication_ts` is an acceptable availability timestamp and a bounded freshness expectation for the intended cadence. Otherwise this endpoint does not satisfy the contract's availability/freshness evidence.
- Official evidence defining whether `symbol` plus `count=1` returns the latest trade at request time, or another documented retrieval mechanism with equivalent latest-as-of semantics. Until then, do not label a returned trade `LAST_TRADE` as the latest price.
- Review and test of the original-precision-preserving millisecond normalization above, including same-millisecond ordering and decisions close to the cutoff.
- A retention decision and approved schema/privacy boundary for the receipt and fingerprints. Provider permission does not itself authorize persistence or redistribution.
- Separate PAPER account in the matching quote currency (USD for the example pair), exact external instrument mapping, price-age policy, and an explicit decision on how `LAST_TRADE` is used for valuation and simulated fills.
- Security review of server-side credential/egress configuration if the eventual provider requires authentication; no provider data credentials are currently required for this candidate's public endpoint.

| Fixture | Expected outcome |
|---|---|
| Valid expected pair, USD quote, known MIC, positive decimal price, ordered match/publication/retrieval/cutoff timestamps | `AVAILABLE`; exact integer conversion and stable provenance fingerprint |

| `trade_ts` or `publication_ts` in the future; reversed timestamp order; stale observation beyond configured age | Blocked temporal validation; no price |

| USD quote supplied to NOK account | Currency mismatch; no implicit FX or account conversion |

These are proposed synthetic test cases, not executed tests or observed provider responses.

## Gaps and next step

This review selects a **conditional candidate**, not an approved source. Current exact pair/venue mapping, latest-trade selection semantics, source-time precision mapping, legal usage and retention rights, `publication_ts` availability qualification, freshness SLA, and exact cost remain unresolved. Alpaca is also not authorized by its public API. Coinbase remains blocked. The existing fixture worker stays explicitly synthetic and unchanged.

**Permission gate:** written use permission blocks external provider ingestion and use, including validation against that provider. Offline implementation of the adapter boundary, parsers and contract tests using synthetic responses can continue without external data or credentials, provided it remains clearly separated from acquisition and cannot be enabled as an external source. No real provider request or persistent provider data is permitted until the required usage/storage/display approval and technical qualification are recorded.

Next step: seek written rights/retention clarification and official static pair identity, timestamp precision and latest-trade selection evidence for Kraken Post-Trade. If any gate fails, keep external PAPER blocked and assess another source in a separately documented review. Offline synthetic implementation may proceed as a separate code slice; external acquisition/use remains gated. No hosted changes, policy activation, worker start, live data calls, or actual trading are part of this review.
