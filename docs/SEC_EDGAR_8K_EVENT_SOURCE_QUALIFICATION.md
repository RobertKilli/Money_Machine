# SEC EDGAR Form 8-K event source qualification

Contract: `sec-edgar-8k-event-source-qualification/v1`. Review control time: 2026-09-30 07:17 UTC. This qualifies a bounded SEC source profile; it does not retrieve filings, parse filing text, issue events, persist data, or enable a scheduler or signal.

## Scope and decision

**PARTIAL.** Scope is public SEC EDGAR registrant submissions for Form `8-K` and `8-K/A`, jurisdiction US, regulator SEC. Form `6-K`, `10-K`, `10-Q`, registration statements, filer submissions/authentication APIs and XBRL facts are separate or unsupported profiles. The submissions API may contain those other forms, but its existence does not extend this source qualification to them.

| Profile | Host/path | Role and limit |
|---|---|---|
| `COMPANY_SUBMISSIONS_JSON` | `data.sec.gov/submissions/CIK{10-digit-zero-padded-CIK}.json` | Filing metadata/history by filer CIK; reconcile by accession and form, not company ticker/name. |
| `SUBMISSIONS_HISTORY_JSON` | `data.sec.gov/submissions/{filename}` where filename is referenced by that CIK's current submissions record | Referenced history file; keep filename within the same CIK scope. |
| `FILING_INDEX` | `www.sec.gov/Archives/edgar/data/{unpadded-CIK}/{accession-without-dashes}/{accession-dashed}-index.htm` | Filing-scoped index/header and document list; locate primary document and exhibits. |

| `EXHIBIT_DOCUMENT` | Same accession directory plus an index-listed exhibit filename | Supporting filing artifact; exact document type/content format is inspected later, not fetched here. |

The RSS query keys are fixed by its profile; arbitrary query parameters are rejected. The supported set is intentionally narrower than the SEC's submissions/XBRL APIs. ## Filing identity and time semantics

The filing key is the tuple `(normalized 10-digit CIK, accession number, form)`. CIK is zero-padded to ten digits in the submissions endpoint; the archive directory uses the CIK without leading zeros. Accession is represented canonically as `##########-YY-######`; its archive directory form removes dashes. SEC documentation notes that the accession's leading CIK can identify the submitting filer agent, so registrant CIK must be separately read from filing metadata/header. Ticker and name are lookup attributes, not issuer identity. A filename or URL is only a locator.

The archive index binds filing metadata and ordered document entries, including sequence, type and filename. The primary document and each exhibit get separate content fingerprints; filing metadata has a different fingerprint. The same accession discovered in RSS, submissions JSON and archive index reconciles to one filing. Filing acceptance, filing date, report date/period, signing date, event announcement, expected closing, completion and local receipt are distinct timestamps. The submissions JSON exposes fields such as accession number, form, filing date, report date, primary document and acceptance datetime where present. Acceptance time is EDGAR processing time, not the underlying event time. [DOCUMENTED: SEC, “EDGAR Application Programming Interfaces (APIs)”, https://www.sec.gov/search-filings/edgar-application-programming-interfaces; “Webmaster Frequently Asked Questions”, https://www.sec.gov/about/webmaster-frequently-asked-questions; “Accessing EDGAR Data”, https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data; checked 2026-09-30 07:17 UTC.]

Form 8-K is a current report. Item 1.01 concerns entering a material definitive agreement, including agreements subject to conditions; it does not mean an acquisition completed. Item 2.01 concerns a consummated significant acquisition or disposition, but item number alone does not establish crypto-asset identity or every event detail. Other items may be relevant. The filing text and exhibits require later document review; forward-looking statements and expected closing are not completion. Form 8-K/A is a separate amendment filing. Link it to an original only when explicit document/material evidence supports that relation; the form suffix and recency alone do not identify the parent. Preserve original metadata and document fingerprints, append a correction/supersession edge, and never overwrite or newest-win. SEC documents same-business-day post-acceptance corrections in that evening's indexes; later removals may not appear in prior daily/feed/oldload indexes, while full and quarterly indexes are rebuilt weekly. A single response therefore cannot prove complete correction history. [DOCUMENTED: SEC, “Form 8-K”, https://www.sec.gov/divisions/corpfin/forms/8-k.htm; “Compliance and Disclosure Interpretations: Exchange Act Form 8-K”, https://www.sec.gov/files/divisions/corpfin/guidance/8-kinterp.htm; “Accessing EDGAR Data”, https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data; checked 2026-09-30 07:17 UTC.]

## Pagination, history, latency and completeness

The submissions recent record uses parallel filing-field arrays. The local metadata adapter validates array shape and equal lengths before zipping by row index; it accepts zero recent rows so a referenced history file can be considered. It validates general row field types and accession/date/filename syntax across the list, but compares the selected filing's exact form, filing date, and primary filename only on the row with the selected accession. It does not require unrelated rows to match the selected filing or fixture. Missing fields, non-array field values, non-string array elements, semantic row errors, and unequal array lengths have distinct fixed diagnostic reasons with no response values. JSON/Atom responses must be decoded as UTF-8. Filing document media type and declared character encoding must be validated at acquisition, and unsupported formats fail closed. This section records application policy; it does not establish response-specific charset behavior. [DOCUMENTED: SEC, “EDGAR Application Programming Interfaces (APIs)”, https://www.sec.gov/search-filings/edgar-application-programming-interfaces, checked 2026-09-30 07:17 UTC; validation and UTF-8 rejection behavior are application policy, not SEC guarantees.]

Company submissions JSON contains at least one year or the latest 1,000 submissions (whichever is more); older filings are referenced by additional historical submission files. The JSON API updates through the day as filings disseminate; the `submissions.zip` snapshot is republished nightly at approximately 3:00 a.m. Eastern. Reconciliation must process recent rows, discover and fetch referenced historical files, and compare nightly bulk snapshots without assuming these mechanisms alone prove complete event coverage.

Latest Filings and RSS can filter by company, CIK, or form. Historical Archives search can be ordered alphabetically and its index may lag one business day. RSS/search is useful for discovery, not completeness. SEC reports typical submissions processing under one second and document availability often within one to three minutes, while warning those delays can increase; they are not end-to-end service guarantees. **UNKNOWN:** exact request pagination/update guarantees for every feed/search profile, source-wide completeness, and a stable content-availability timestamp. [DOCUMENTED: SEC, “EDGAR Application Programming Interfaces (APIs)”, https://www.sec.gov/search-filings/edgar-application-programming-interfaces; “RSS Feeds”, https://www.sec.gov/files/about/secrss.shtml; “Accessing EDGAR Data”, https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data; “Webmaster Frequently Asked Questions”, https://www.sec.gov/about/webmaster-frequently-asked-questions; all checked 2026-09-30 07:17 UTC.]

## Fair access and future request-plan boundary

SEC requires an identifying User-Agent with contact details and documents a maximum of 10 requests per second across SEC.gov access. This is the provider-documented ceiling, not a target; production request scheduling/concurrency still requires a reviewed budget. Excessive or unclassified automated access may be rate-limited or blocked. The pure request-plan contract records identity by a non-secret approved reference and proposes broader retry bounds; the local smoke transport described below applies stricter run-specific limits, no retries, and rejects redirects. SEC endpoint-specific retry and caching/conditional-request guarantees are **UNKNOWN**; a future client must honor provider cache headers when present and avoid redundant retrieval. The transport does not change the qualification or production decision and cannot run without an independently pinned authorization. ## Local EDGAR transport smoke proposal — 2026-10-06 11:36 UTC

The isolated implementation adds a server-only staged HTTPS GET flow. It starts from one authentic company-submissions plan. If the validated recent rows contain the exact accession, it derives the fixed filing-index plan. Otherwise it selects at most one referenced historical file whose inclusive `filingFrom`/`filingTo` range contains the target filing date; ambiguity or absence stops the run. The history plan is derived internally from the authenticated first-stage plan and selected manifest filename, and its response must validate the exact filing identity before the filing-index request. Callers cannot submit a history filename or a preassembled three-request batch to this flow. One authorization object is consumed for the entire run, including all stages; the aggregate cap is three requests. Request starts are spaced by at least one second process-wide, there are no retries, each request has its own 10-second timeout and 2 MiB cap (there is no separate whole-run timeout), compressed bodies and all redirects are rejected, and source qualification plus authorization are rechecked before every request start. The public transport result exposes only status/content type/byte length/SHA-256 observations. Bounded bodies are held behind module-local authentic exchange references for server-side parsing; they are not returned in public transport results or logged. Intermediate response bodies are one-shot and cleared after preflight parsing; the final exchange bodies expire after 60 seconds if unconsumed and are cleared after adapter consumption, failure, or abort. The operational `LOCAL_SMOKE` authorization registry remains empty, so no live request is currently possible.

Failed or aborted runs clear already accumulated body buffers. These are process-memory bounds, not durable erasure guarantees for runtime copies held internally by Node.

## Submissions schema diagnostics — 2026-10-07

The submissions adapter treats `acceptanceDateTime` as optional, consistent with the SEC API description that this field is present where available. A missing array is synthetically verified to fall back to the filing-index `Accepted` value; if both sources provide a timestamp, a disagreement is rejected as an identity conflict. A supplied value of the wrong type or an array length that differs from its parallel filing arrays remains rejected.

The former `SEC_SUBMISSIONS_SCHEMA_INVALID` outcome was reproduced with a synthetic submissions response that omitted `acceptanceDateTime`. That demonstrates one concrete failure mode and the corrected fallback. The bytes from the earlier live attempt were not retained, so the actual cause of that live failure remains unknown. Bounded diagnostics distinguish transport status/content type, UTF-8/JSON parsing, and schema failures using only fixed stage/reason/field codes. They do not include response values, body excerpts, raw bytes, or operator contact. No live SEC request was made for this diagnosis.
