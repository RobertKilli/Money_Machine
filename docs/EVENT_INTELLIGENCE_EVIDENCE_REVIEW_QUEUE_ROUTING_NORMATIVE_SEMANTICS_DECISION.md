# Evidence review queue routing normative semantics decision

**Decision status:** recommended future contract behavior only. This document does not change the current routing decision, routing material, evaluator, queue classifier, tests, or production configuration. No recommendation here is implemented or approved for production.

## Purpose and evidence boundary

This decision resolves two ambiguities in `event-intelligence-source-portfolio-routing-decision/v1`: what `RETRACTION_WITHDRAWAL` means relative to the `retracted` input, and what an event route's `required` state means. It records current declarations and observable behavior separately from the recommended future behavior.

Tracked evidence reviewed includes `src/domain/intelligence/event-intelligence-source-portfolio-routing-decision.ts` (`EVENT_ROUTE`, `evaluateSourcePortfolioRouting`, `parseSyntheticRoutingMaterial`, and the previous-result guards), `src/domain/intelligence/event-intelligence-news-discovery.ts` (record parser and `sealDiscoveryOriginSet`), `src/application/intelligence/compose-event-intelligence-evidence-review-queue.ts` (`assertCandidateBinding` and composition loop), and `src/domain/intelligence/event-intelligence-evidence-review-queue.ts` (`classify`, blocker and priority functions). The routing and queue tests, routing decision document, and routing semantic-material document provide additional contract and regression evidence.

The evaluator accepts only the built-in module-authentic routing decision and structurally valid synthetic input. Its progression outputs are module-local authenticated results bound to that decision and candidate context. This protects the in-process sequence; it does not make caller-supplied synthetic facts, source statements, or policy application authoritative. Composition additionally requires module-authentic news-discovery candidates, derives the event hint and `retracted` value from their synthetic discovery records/lifecycle set, binds those values to the route input, and returns `NON_AUTHORITATIVE_SYNTHETIC_COMPOSITION`. None of those boundaries supplies external retraction authority or production approval.

## Retraction and withdrawal

Separate the subjects:

* `eventHint = RETRACTION_WITHDRAWAL` says the candidate describes a withdrawal/retraction of the underlying business event. It is a claim requiring lifecycle review; it does not by itself say that this source record has been withdrawn.
* `retracted = true` is currently a broad candidate-lifecycle flag. It does not identify its lifecycle subject. In the direct routing API it is only a parsed boolean. In the current synthetic composition path, `assertCandidateBinding` derives it from a record's `lifecycleHint.kind === RETRACTION` or the sealed local discovery set's `RETRACTED` lifecycle status. That status is assigned both to a candidate whose own hint is `RETRACTION` and to an earlier candidate whose successor is a retraction. The flag therefore cannot tell whether the source document was withdrawn, the candidate's claim was retracted, or an earlier claim was superseded. A **retraction** says a claim is withdrawn; **supersession** says a later revision replaces an earlier one. They are not synonyms, and a source document's availability/lifecycle is a third distinct subject. These synthetic, module-local facts are not an applied external source registry or proof of real-world retraction.

The discovery record parser validates `lifecycleHint.kind`, its target-candidate shape, correction/retraction event category, provider/source type, and timestamps. `sealDiscoveryOriginSet` checks same-origin and chronological parent/child constraints and derives `ACTIVE`/`CORRECTED`/`RETRACTED`. It does not establish the truth of the declaration. The routing evaluator itself receives neither the discovery record nor the origin set, so a direct call can supply `retracted` independently of the hint. Composition rejects a disagreement between the source-derived expected hint/flag and route material.

### Current behavior and recommended behavior

The table assumes all other input is valid, a supported non-dual-listed jurisdiction, no conflicts, rights/credentials/qualification/mapping/source gates pass, no duplicate, and no independently unresolved correction. “Current route” is the first call from `DISCOVERED`. Queue behavior describes the existing projection classifier if given the resulting authentic routing result.

Do not erase its target/parent relation. | Requires the same typed lifecycle/routing changes plus queue status/action alignment; tests must separate the affected subjects and relation. |

The evaluator's control order is material here: the top-level `retracted` guard blocks before state-specific branches; `eventHint` contributes degradation and primary-stage selection, but is not a top-level stop guard. `retractionStops` in the decision row is currently declarative only. Existing routing tests pin the four direct-evaluator combinations. At composition, `RETRACTION_WITHDRAWAL` with `retracted=false` is rejected, but non-retraction event hints with `retracted=true` can represent an earlier candidate whose lineage is marked `RETRACTED` after a retraction successor; a retraction-hint candidate itself is also marked `RETRACTED` by the current origin-set derivation. This confirms the current field/status does not distinguish lifecycle subject or relation. Direct API acceptance of all four pairs is not evidence of equivalent authentic source facts. In v2, either `retracted=false` is supported with explicit typed lifecycle context, or the bare boolean is rejected; a true boolean alone must never be reinterpreted as “superseded.”

### Recommendation

Adopt the distinction in the table: a hint that reports an event retraction creates a mandatory correction/retraction review obligation; an authenticated retraction of the candidate's claim stops ordinary progression for that claim; and supersession is a separate relation that preserves the predecessor as historical and points to its successor. A source document withdrawal is separately represented and stops use of that document as active evidence. Do not make the event hint alone a terminal stop. A report that an acquisition was withdrawn can itself be the evidence needed to investigate the lifecycle; treating every such report as terminally ineligible risks bypassing the review that determines which claim changed and whether correction/retraction lineage is complete. A superseded or retracted claim must not continue as an active claim, but the successor/report and lineage must remain reviewable.

The current `retracted` boolean is insufficient as a durable or production proof. A future contract must replace it with typed, subject-specific lifecycle facts: (a) source-document state and document identity; (b) candidate/event-claim state; and (c) an explicit `SUPERSEDES`/`CORRECTS`/`RETRACTS` relation to its target revision where applicable. The evidence must bind each subject and relation to the exact discovery candidate/reference, origin, evaluation cutoff, and parent/successor identities, and establish that the relation is accepted by the responsible source/provenance contract. A module-local `WeakSet` marker or caller declaration alone is not that authority. It must retain the event hint separately. `correctionResolved` is likewise a synthetic boolean today; it cannot stand in for an authenticated lineage review result.

The review item must remain present even when route status is terminal. Duplicate/no-action must not suppress retraction or correction lineage. The current queue classifier's hint-first mapping labels hint-only material `RETRACTED`; this conflates an event-retraction report with lifecycle status. Since `blockersFor` adds `RETRACTION_PRESENT` only from `result.retracted`, a hint-only item can have that `RETRACTED` classification without the corresponding blocker code. This is a downstream queue alignment issue, not changed here. The existing queue projection gives the classification precedence over duplicate, which preserves a review item, but its status vocabulary needs distinct unresolved event-retraction, superseded-claim, retracted-claim, and withdrawn-source meanings before this recommendation can be applied.

## Meaning of `eventRoutes.required`

### Current declarations and behavior

The decision has a row for every event hint. `CORRECTION_AMENDMENT` and `RETRACTION_WITHDRAWAL` declare `CORRECTION_REVIEW_REQUIRED`; `BINDING_AGREEMENT` and `COMPLETED_PURCHASE` declare `PRIMARY_DISCLOSURE_REQUIRED`; other hints declare `SOURCE_RETRIEVAL_REQUIRED`. `COMPLETED_PURCHASE` separately sets `completionEvidenceRequired=true`; retraction hint separately sets `retractionStops=true`.

| Event hint group | Current declared `required` value | Other current row flag |
|---|---|---|
| `CORRECTION_AMENDMENT`, `RETRACTION_WITHDRAWAL` | `CORRECTION_REVIEW_REQUIRED` | `retractionStops=true` only for `RETRACTION_WITHDRAWAL` |
| `BINDING_AGREEMENT`, `COMPLETED_PURCHASE` | `PRIMARY_DISCLOSURE_REQUIRED` | `completionEvidenceRequired=true` only for `COMPLETED_PURCHASE` |
| All other hints, including `UNKNOWN` | `SOURCE_RETRIEVAL_REQUIRED` | Both additional flags false |

The evaluator does not read `eventRoutes.required`. Every initial evaluation starts at `DISCOVERED`, then follows the shared ordered transitions. The returned `eventHint` is carried into each authenticated previous-result chain, whose candidate binding also fixes `evaluationAsOf`. A blocked/terminal previous result cannot progress. `UNKNOWN` and `DUAL_LISTED` have their own stop behavior. The `required` field therefore currently has no runtime effect and does not select an initial state, jump over stages, or prove that a milestone was completed.

### Recommendation: mandatory review milestone

In a future contract, define `required` as the event-specific **mandatory review milestone**, not an aspirational target and not a terminal destination. It means:

1. The route starts at `DISCOVERED` for every new candidate. `required` never changes that initial state or grants a shortcut.
2. Reaching a state and completing its review are separate facts. The milestone is complete only when an authenticated evaluation is made *from* that milestone, its milestone-specific gates pass, and a typed review outcome is bound to that evaluation. Merely returning the milestone as `nextState` is arrival, not completion.
3. No ordinal/rank comparison between states is allowed. A later state can satisfy an earlier milestone only if authenticated transition evidence proves the legal path and includes a successful evaluation from the required milestone. State labels or a history array alone are insufficient.
4. A `STOPPED_BLOCKED`, malformed, copied, mismatched, terminal, or otherwise unauthentic prior result cannot satisfy the milestone or authorize progression. Evidence must bind the decision fingerprint, candidate and its relevant immutable context, previous result, exact milestone, evaluated inputs, outcome, and fixed cutoff. The responsible module must issue it at the time it evaluates that milestone; a later caller declaration cannot recreate it.
5. The existing evaluator's module-local `WeakSet`/`WeakMap` authenticates a result object and its accumulated transition history: the map retains the decision fingerprint, candidate binding, history, and canonical result, and each next call requires the authentic prior object. However, the public result/history does not contain a distinct milestone-review outcome, and the current `correctionResolved` input is a synthetic boolean. It therefore supports authentic progression sequencing, not authenticated review completion. A new closed, versioned milestone-evidence contract and issuer/checking boundary is a prerequisite before `required` can be enforced normatively.
6. At a retraction/correction milestone, unresolved or missing lifecycle evidence holds progression and remains reviewable. A local review outcome is still not event authority, policy approval, or proof that the underlying claim is true.
7. A required milestone that cannot be reached under jurisdiction/source constraints remains unsatisfied and blocked; it does not trigger opportunistic fallback to a weaker route. The cutoff is fixed for an evaluation chain. Evidence available only after that cutoff cannot complete a historical milestone at the earlier cutoff; evaluate a new, later snapshot/evaluation and preserve the earlier one append-only.

For `COMPLETED_PURCHASE`, the separate completion-evidence requirement remains an additional gate at primary disclosure; merely reaching or completing the milestone does not satisfy it. “Required” should be renamed in a future contract to `requiredReviewMilestone` (or another equally explicit name), because the current name invites a target-state interpretation. The existing declaration's event-specific state values can seed that future meaning, but do not yet enforce it. The milestone-evidence contract described above is missing and must be specified before runtime alignment; the existing accumulated state history is not a substitute for it.

This interpretation makes the field meaningful without inventing ordinal status semantics. Since the current graph already routes every successful candidate through shared stages, most current rows will be reached as part of that path; the declaration still becomes a named, testable event-specific gate for future graph changes. The alignment contract must say whether a mandatory checkpoint is considered complete by stage arrival alone or only by a nonblocked result whose stage conditions were satisfied. This decision recommends the latter.

## Related routing observations

* **`DUAL_LISTED`:** the parent jurisdiction table has no dedicated row. Runtime `routeOrder` falls back to the aggregator family, then a separate blocker stops the candidate. A blocked result can therefore carry `nextSourceFamily=DISCOVERY_AGGREGATOR`. The future milestone rule must not treat a suggested source family as evidence that a required milestone was reached.
* **`primaryNeeded`:** at `PRIMARY_DISCLOSURE_REQUIRED`, the event-specific branch and ordinary primary-disclosure fallback yield the same decision fields (`nextState`, history, degradation, priority, and authority flags) after prior guards. The returned `eventHint` and `routingResultId` still differ. The branch has no separate route effect in the current evaluator; do not claim otherwise.
* **`FILING_AUTHORITY`:** the synthetic routing parser accepts it as a family, and the composition checks family against the authenticated discovery `sourceType`. Current discovery source types are `NEWS_AGGREGATOR`, `ISSUER_IR`, `NEWSWIRE`, and `EXCHANGE_OR_REGULATOR_FEED`; none maps to `FILING_AUTHORITY`. Synthetic evaluator acceptance is not evidence that current news discovery can produce a filing-authority candidate.
* **Source lifecycle:** discovery's `lifecycleHint` is a validated synthetic declaration tied to a candidate ID. The origin-set builder verifies target existence, same declared origin, and temporal ordering before deriving lifecycle status. Composition then binds that status to route input. This is stronger than an unbound boolean within the module, but the current `RETRACTED` label combines a retraction-report candidate with its superseded target and does not prove an external source actually retracted a document.

## Prerequisite and future alignment plan

This cannot safely be one runtime-alignment slice yet. First, a design-only prerequisite must define the milestone/lifecycle evidence contract and its trust boundary. Only after that contract is reviewed can a separate, narrowly scoped routing/queue alignment implement it.

The prerequisite must decide: (1) which module issues and verifies milestone evidence; (2) the exact typed subjects and relations for event claim, candidate claim, source document, and `SUPERSEDES`/`CORRECTS`/`RETRACTS`; (3) what stage inputs and outcome prove a milestone review passed; (4) how decision, candidate/reference, origin, previous result, and cutoff are bound; (5) which outcomes hold, pass, or terminate progression; and (6) how evidence that appears after a historical cutoff is represented without rewriting the old evaluation. A `WeakSet`/`WeakMap` authenticity marker can guard module-local objects, but must not be treated as a real-world source authority or policy approval. Existing `stageHistory` proves the accumulated transition sequence; it does not carry this typed review outcome.

After that prerequisite, the runtime alignment should:

* Replace/clarify `required` with a mandatory milestone field and enforce it using the reviewed evidence contract, fixed cutoff, and fail-closed behavior.
* Separate event-retraction claims, candidate-claim lifecycle, source-document lifecycle, and supersession relations in typed input/output fields. Bind these to discovery/provenance material rather than a free boolean; do not mint external authority.
* Hold an event-retraction hint at the correction/retraction review milestone until a bound review outcome exists. Stop ordinary progression for a retracted claim or withdrawn source only according to the typed subject; keep superseded claims historical and preserve their linked lifecycle evidence and review item.
* Version a clarified declaration as a new source-portfolio decision contract and routing semantic-material profile (v2 rather than silently redefining v1). The hint-only correction-review hold changes evaluator behavior and therefore needs a new declared routing algorithm version (v2). A pure naming clarification with no behavior change still needs a new declaration/material version, but does not by itself imply a new algorithm version.
* Update queue contract/material separately to distinguish an `EVENT_RETRACTION_CLAIM_REVIEW`, a `SUPERSEDED_CANDIDATE`, and a `SOURCE_DOCUMENT_RETRACTED` condition; avoid hint-only `RETRACTED`, preserve correction/retraction visibility ahead of duplicate/no-action, and pin priority/status/action precedence. Give the changed queue semantics a new queue contract/material version.
* Add four-combination tests at the direct evaluator boundary, composition tests for lifecycle subject/relations, event-milestone gate tests, blocked/copy/mismatch previous-result tests, and queue projection collision tests against duplicate, correction, and other blockers. Each negative fixture must first pass the earlier parser/authenticity gates it is intended to test.

Changing the semantic inputs represented by the routing policy reference may require a future scope-material/profile version update before policy content identity can be used. The existing scope v1 identity and its `canonicalMaterialDigest` meaning must not be reinterpreted to imply content verification. A new declared algorithm version or a passing conformance sample is not proof that that algorithm was applied in a later composition.

The recommended next prerequisite is the design-only milestone/lifecycle evidence contract above, because the existing evaluator authenticates progression objects but carries only synthetic correction/retraction booleans and no typed review outcome. The later routing alignment depends on that distinction and cannot safely define how `required` is enforced until it exists.

## Open blockers and non-authority

The queue blockers remain unresolved and outside this decision:

* The parent `conflictActionOrder` puts amount/currency before lifecycle conflicts, while runtime `conflictAction` is lifecycle-first.
* Parent `routingMappings` precedence does not match the actual ordered branches in queue `classify`.

This decision does not resolve source-portfolio material closure, issuer/listing policy content, authenticated external source lifecycle authority, policy application, manifest completeness, content identity, producer provenance, storage/read selection, or production approval. It changes no runtime or production configuration; all production selections remain null/empty, approvals remain `NOT_APPROVED`, and authority upgrade remains `UNSUPPORTED`.

The design-only prerequisite for typed milestone and subject-lifecycle evidence is now specified in [the milestone/lifecycle evidence decision](EVENT_INTELLIGENCE_EVIDENCE_REVIEW_QUEUE_MILESTONE_LIFECYCLE_EVIDENCE_DECISION.md). It does not implement issuers, evidence, or routing enforcement; runtime alignment remains blocked on the authority contracts described there.
